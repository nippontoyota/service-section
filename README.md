# BillDesk

Think before you print.

A staff-ID login for advisors, cashiers and super admins. Advisors upload digital PDFs; service amounts, dates and customer identifiers are extracted automatically. Cashiers mark bills paid in one action, which approves the invoice and records its full payment together. Admins inspect customer-grouped bills, full collections, unpaid invoices, original PDFs and an audited history.

For Vercel setup, environment variables and database prerequisites, see [DEPLOYMENT.md](DEPLOYMENT.md).

## Local demo

Run npm install, then npm run dev. In .env.local, set SERVICE_DESK_DEMO=true with no Supabase credentials. Demo mode is development-only and cannot run in a production build.

| User ID | Password | Workspace |
| --- | --- | --- |
| cashier01 | CashierDemo!2026 | Mark bills paid |
| advisor01 | AdvisorDemo!2026 | PDF uploads and own bills |
| admin01 | AdminDemo!2026 | Reports, bill drill-down, staff accounts |

These are also the owner-requested initial credentials for the shared database after bootstrap. In local demo mode, staff changes, approvals and collections persist in this browser (localStorage); uploaded PDFs use IndexedDB. Separate demo devices do not share workflow changes. The shared database uses salted password hashes and server sessions instead.

The local workspace automatically parses and imports these owner-supplied PDFs from the project directory:

| File | Owner-provided type | Extracted invoice | Extracted total |
| --- | --- | --- | --- |
| ATA545.pdf | Counter sales | AA26-01545 | ₹14,881 |
| ACA1145.pdf | Accessories · non-TGA | ACA/26-27/1145 | ₹40,752 |
| INA2600101.pdf | Insurance claim | INA26-00101 | ₹41,305 |

The displayed fields are generated by the same parser as uploaded PDFs, not copied from this table. The type labels are owner-provided annotations. The records are submitted for review, with no fabricated approvals or collections. The local screen starts in the all-dates bill archive because the invoice dates precede the current month. Original PDFs are accessible through View original PDF.

The six old built-in dummy bills and their related simulated history are removed on refresh. A pre-import browser snapshot is saved under service-desk-before-reference-import; other uploads, staff and approvals are preserved. Content hashes and page ranges make repeat imports idempotent. The source PDFs remain on disk and are excluded from version control; they are never copied to public/. This local import and PDF-serving endpoint are disabled in production. Synthetic financial records are used only in unit tests, not the application.

Amounts cannot be manually entered. The parser reads labelled service invoice totals, invoice dates and customer identifiers from digital PDFs. Repeated headers on continuation pages stay in one invoice. Missing/ambiguous totals require a corrected digital PDF; scanned-image OCR is not included.

Advisors can select up to ten PDFs and click **Upload selected PDFs**. Two files process at a time, with individual progress and retry messages. Review cards preserve selection order and show the filename and page range; **View bill** opens the original PDF at that bill's starting page. **Submit for cashier review** confirms each PDF separately, retaining failed submissions for retry. Every remaining bill from a multi-bill PDF is submitted together. Before submitting, advisors can enter an optional token number for each bill from the separate token machine. Leading zeros and prefixes are preserved. The token appears in the cashier list and bill details and can be searched.

Advisors can delete their own unsubmitted drafts from the review card or bill dialog after confirmation. Submitted/approved bills cannot be deleted. A server-side upload claim prevents deletion racing with submission or another deletion. Other bills sharing the PDF remain; deleting the final bill also removes the upload and requests deletion of its stored PDF. Storage cleanup failures are reported explicitly. No new database migration is required for these actions.

Uploaded documents are classified from PDF headings, invoice prefixes, billed parties, job references and repair descriptions. Filenames are not classification inputs. Supported samples include customer service, body-and-paint customer/insurance invoices, Toyota/Assurant extended warranty, warranty repair notes, free maintenance (FMSC) and Toyota Smiles/AMC service notes. Generic warranty terms printed on an ordinary invoice do not make it a warranty bill. Unknown formats remain unclassified or generic tax invoices.

The vehicle owner/consignee is stored as the customer; the billed party is retained separately, so a warranty provider or insurer does not replace the customer name. Classification and its evidence are persisted in `bills.field_confidence.document` alongside the existing extraction metadata. The original customer ID, VIN, registration and job reference remain available for verification. Warranty/AMC notes with no numeric total show “No amount stated”; they remain in the archive and related customer documents, without fabricated zero-value invoices, pending collection requests or payments. Numeric invoices stay in the cashier Overview until marked paid.

The twelve historical PDFs in `bills/` have content-based regression checks in `lib/pdf/extract.test.ts`. Their expected customer values are kept in the ignored local file `samples/private/bill-expectations.json`; these private checks skip when the fixture or PDFs are absent. The reviewed import contains eight monetary invoices and four supporting notes, grouped into ten customers; `output/bill-review/verified-bills.csv` records the verified classifications and linkage. These are shared records uploaded through the advisor workflow, not automatic demo fixtures.

The cashier has two sections: Overview contains all submitted bills awaiting payment, including previously approved unpaid bills; Archive contains paid bills and supporting notes. **Mark as paid** approves and records the full invoice amount atomically, then moves the bill to Archive. Cashiers must choose Cash, GPay, Cheque, Demand Draft or Other before confirming. Other reveals a required field to specify the method. The saved method appears in collection history. There is no separate approval step or manual amount, partial-payment or remaining-balance form. Receipt fragments inside PDFs do not create payments. No payment gateway charge is performed.

The cashier Overview also shows daily billed value, paid bill count/value and unpaid bill count/value. The date picker defaults to today in Asia/Kolkata and groups submitted invoices by invoice date, using their current payment status (including later payments and reversals). Pending invoices are included; supporting notes are excluded and unread amounts are flagged. The pending bill list below continues to show all dates.

Customer groups use customers.id as the primary key and bills.customer_id as the foreign key: one customer can have many bills. An exact normalized Customer ID from the PDF is the preferred identity, including across multiple vehicles. If absent, exact normalized name + VIN (or registration) forms a provisional group. Names alone never merge records; bills without sufficient identity remain separate. Documents with and without Customer ID are not silently merged across those identity types. Invoice/job-card references identify bills or visits, not customers. The group totals and related-bill links respect the logged-in role's visibility.

## Real staff and shared records

1. Configure a development Supabase project. Apply migrations in order:
   - supabase/migrations/202610230001_initial.sql (new projects only)
   - supabase/migrations/202611040001_staff_finance.sql
   - supabase/migrations/202611040002_customer_full_payment.sql
   - supabase/migrations/202611040003_app_auth.sql
   - supabase/migrations/202611050001_atomic_upload_confirmation.sql (apply before deploying the new confirmation endpoint)
   - supabase/migrations/202611050002_cashier_mark_paid.sql (apply before deploying the one-step cashier payment flow)
   - supabase/migrations/202611070001_payment_method_and_token.sql (apply before deploying payment methods and token entry)
   - supabase/migrations/202611100001_admin_chosen_password.sql (apply before deploying admin-chosen staff passwords)
2. Set NEXT_PUBLIC_SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY in .env.local. Set SERVICE_DESK_DEMO=false. The publishable/anon key is no longer required. Never expose the secret/service-role key in frontend variables. Supabase supplies database and private PDF storage; staff login does not use Supabase Auth, emails or Auth dashboard settings.
3. Run npm run bootstrap:staff. It installs individually salted scrypt hashes for admin01 / AdminDemo!2026, cashier01 / CashierDemo!2026 and advisor01 / AdvisorDemo!2026. Existing profile IDs and bill history are preserved. A repeat run does not overwrite passwords already configured in staff_credentials. The three initial accounts are usable immediately; additional admin-created accounts use the 6–8 character password (any characters; no complexity requirements) chosen by the admin and can sign in immediately. Password resets still issue temporary passwords that must be changed at first login. Known initial passwords are not made private by hashing; reset them before opening the app to untrusted users.
4. Restart the app. The admin can create further individual staff accounts, reset passwords and disable access. User IDs use 3–40 lowercase letters, digits or underscores. There is no public signup or email recovery; the admin resets staff access.
5. Before enabling the new app, stop any existing external purge schedules. The migration clears expiry dates, enforces permanent retention and unschedules matching Supabase cron jobs. Deploy the retired purge-paid function too if the original function was previously deployed. It now returns 410 and deletes nothing.

Paid bills, PDFs and audit records are retained. Existing bills without financial values remain pending and excluded from financial totals. Admin can open those bills and choose “Re-read original PDF”; the cashier can then mark the bill paid once payment is collected. No historical collection is inferred from the old paid marker. PDFs already deleted by the previous retention policy cannot be recovered by this migration.

Production demo fallback is disabled: a production build without Supabase configuration shows a setup notice instead of simulated authentication.

The app-auth migration detaches profiles from auth.users without deleting existing Auth users or business records. Old Supabase Auth JWTs lose direct access to the app's tables, RPCs and PDF storage. Existing staff beyond the three initial accounts need an administrator password reset to initialize their new credential record. Previously generated Supabase Auth passwords no longer sign in to BillDesk.

Passwords are verified on the server with Node's scrypt (N=32768, r=8, p=3), a random salt and constant-time comparison. Only the encoded hash reaches staff_credentials; no plaintext password is stored in Supabase or audit events. Use HTTPS when deployed: the browser submits the password to the app server, which hashes it before database writes. Database hashes are not accepted as login passwords.

Sessions use random HttpOnly, SameSite=Strict cookies (Secure in production), expire after 12 hours and store only SHA-256 token digests in staff_sessions. Logout, password changes/resets and account access changes revoke sessions. Sign-in is limited to 10 attempts per staff ID per 15 minutes. POST routes reject cross-origin requests. Credential/session tables and identity-bearing RPCs are server-only; every app route validates the session and role, and database functions enforce financial and staff-management permissions too.

## Reporting rules

- Admin Overview shows three clickable counts across all dates, optionally filtered by uploading advisor.
- Total paid bills: submitted invoices currently paid in full, with their total invoice amount underneath. Each bill counts once; reversals move it back to unpaid.
- Total unpaid bills: all submitted invoices not currently paid in full, including those awaiting approval, with their total invoice amount underneath.
- Awaiting approval: the subset of unpaid invoices not yet approved by the cashier. Drafts and supporting warranty/AMC notes are excluded from all three counts. Unread amounts are counted as unpaid bills but excluded from monetary totals and flagged.
- INR is stored in integer paise. Dates are displayed and grouped in Asia/Kolkata.
- Every clickable metric uses the same snapshot and filters as its underlying rows. Search filters the displayed rows only and is labelled accordingly.
- Reversing an incorrect payment requires a super admin and a reason. The original payment remains. The negative correction belongs to the reversal date. This is not a refund or credit note.
- Partial/split payments are not supported. A database trigger enforces payment entries equal to the approved invoice total.
- On upgrade, old payment fragments are preserved in archived records. A previously fully settled set is represented by one full-bill collection. Incomplete prior collections are excluded from the current full-payment workflow and require cashier reconciliation; nothing is silently topped up. The transition is audited. Existing demo data is upgraded without deleting uploads or staff accounts.
- Bill totals are not profit or tax-exclusive accounting revenue. Parts/labour analysis, refunds, invoice cancellation, OCR and external platform synchronisation are not included.

## Interfaces and future integration

Internal authenticated routes:
- POST /api/auth/login: staffId and password; sets an HttpOnly app session cookie and returns the profile, never a token or password hash.
- POST /api/auth/logout: revokes the current app session and clears its cookie.
- GET /api/desk: current profile and a consistent bill/payment/staff/audit snapshot.
- POST /api/desk: password, approve, collect, reverse, pdf, reextract, create_staff, reset_staff or toggle_staff.
- Existing upload init/process/confirm endpoints remain; only advisors can use them.
- POST /api/demo/extract: real PDF parsing for development-only demo uploads; disabled in production.
- GET /api/demo/reference-bills: parse the three fixed local reference PDFs. The file query parameter serves only one of those three originals. Disabled in production.

Financial mutations execute through checked database functions, row locking and an append-only payment ledger. Direct browser database access is disabled; the server returns role-scoped snapshots and authorizes short-lived signed PDF URLs. Account status and temporary-password requirements are checked for backend actions.

Submission uses `app_confirm_upload` to confirm the upload and insert its submitted audit events in one transaction. A partial unique index on confirmed PDF hashes prevents duplicate submissions across staff, including simultaneous requests; a retry of the same upload returns its original confirmation without another audit event. The stored SHA-256 hash is reused, so submission does not download or parse the PDF again. Distinct PDFs sharing a job/customer remain valid; changed PDF bytes with the same invoice reference are still protected separately at invoice approval. Apply the confirmation migration before deploying the endpoint. Existing duplicate confirmed hashes cause the migration to stop without deleting or merging documents.

lib/desk.ts contains reporting calculations and typed records. Stable bill/payment/staff IDs and timestamps are retained for a future versioned read API. External API credentials, pagination, company/centre mapping and platform-specific synchronisation belong to that later integration phase.

## Checks

Run npm test, npm run lint and npm run build. Tests cover exact money parsing, ignoring payment fragments, customer-ID extraction/grouping, date boundaries, duplicate collection/reversal requests, data upgrades and report reconciliation. The four supplied sample PDFs are checked when present; keep real PDFs out of version control.

Optional integration checks do not add production dependencies:
- Install @electric-sql/pglite and playwright in a temporary tools directory.
- Set PGLITE_PATH to the installed package directory and run node scripts/check-database.mjs. It runs all migrations in isolated PostgreSQL and tests customer foreign keys, full-payment enforcement, role boundaries, direct-write denial, approval, collection, reversals, account restrictions and retention.
- With the demo server running, set PLAYWRIGHT_PATH to its installed package directory and run node scripts/check-browser.mjs. DESK_URL defaults to http://localhost:3000. It uses a fresh browser context for the upload-to-admin workflow, password changes, PDF preview and mobile layout.

The app-managed login and Supabase Storage need a configured-project smoke test before deploying. Local database tests emulate the legacy auth/storage schemas but do not contact a hosted Supabase service.

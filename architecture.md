## 1. Overview

A small web app with two roles. Service advisors upload bill PDFs. The system reads the text inside the PDF (no OCR, no ML), extracts VIN, vehicle number, and customer name, and stores the bill. The cashier searches and prints bills, then marks them paid. Paid bills are deleted automatically after 24 hours.

```
 Service Advisor (phone/PC)            Cashier (counter PC)
          |                                      |
          v                                      v
   +-------------------------------------------------+
   |        Web app (Next.js, mobile-friendly)       |
   |   Upload page | Dashboard | Bill detail | Login |
   +----------------------+--------------------------+
                          |
          +---------------+----------------+
          v                                v
 Server route: PDF reading         Supabase directly
 (text extraction + rules)         (Auth, search, realtime)
          |                                |
          +---------------+----------------+
                          v
   +-------------------------------------------------+
   |                    Supabase                     |
   |  Auth | Postgres | Storage (private) | Realtime |
   |  pg_cron + Edge Function (nightly/hourly purge) |
   +-------------------------------------------------+
```

## 2. Technology choices

| Layer | Choice | Reason |
|---|---|---|

| Hosting | **Vercel** (or any Node host) | Simple deploys |
| Styling | **Tailwind CSS** | Fast to build readable, large-text screens |
| Backend platform | **Supabase** | Already chosen: Auth, Postgres, Storage, Realtime, scheduled jobs |
| Login | **Supabase Auth** (email + password) | Built in, role stored in a profile table |
| Installable app feel | PWA (web app manifest) | Advisors can add it to the phone home screen; no app store |

## 3. PDF reading (no OCR, no ML)

The PDFs are assumed to be **digital** (generated by software), so the text is already inside the file. We read that text directly and find fields using patterns. Nothing is "recognised from pixels".

### Libraries

| Purpose | Library | Notes |
|---|---|---|
| Extract text per page | **pdf-parse v2** (built on Mozilla's `pdfjs-dist`) | Returns page-level text needed for splitting multi-bill PDFs while keeping one PDF dependency |
| Split pages / build a print-only copy | **pdf-lib** | Creates a new PDF containing only one bill's pages for printing |
| In-browser PDF preview | Browser's built-in PDF viewer (`<iframe>`/`<object>`), optionally **react-pdf** | Keeps the build simple |
| Pattern matching | Built-in regular expressions | No extra library |
| Fuzzy name matching | Postgres extension **pg_trgm** | Runs in the database, not in the app |

Alternative if the team prefers Python: **PyMuPDF** or **pdfplumber** behind a small API. This adds a second service to deploy, so the Node route is recommended for v1.

### How fields are found

1. **Get text** for every page.
2. **Detect bill boundaries.** A new bill starts on a page where a header marker appears (for example "Invoice", "Tax Invoice", or "Job Card"). Pages up to the next marker belong to the same bill. If no marker is found, treat every page as one bill. The markers are kept in a small configuration list, not hard-coded.
3. **VIN:** exactly 17 characters, letters and digits, never I, O or Q. The label "VIN" or "Chassis No." near it raises confidence. A check on the character set rejects most false matches.
4. **Vehicle number:** Indian registration pattern: two letters (state), two digits, one to three letters, four digits (for example `KL 07 AB 1234`). Spaces and dashes are removed for storage; the original spelling is kept for display.
5. **Customer name:** the text after labels such as "Customer Name", "Name", "Bill To", "Customer". Taken up to the end of the line.
6. **Confidence per field:** found next to a label = high, found by pattern alone = medium, not found = missing.
7. **Result:** if all three fields are found, the bill is `ready`. If any is missing or low confidence, it is `needs_review` and the uploader fills it in.

Label lists and patterns live in one configuration file so a new bill layout is supported by adding a label, not rewriting logic.

### Limits to be aware of
- A scanned or photographed PDF has no text and cannot be read automatically. These go to manual entry by design.
- Bill layouts that put the label and value in different table cells may need an extra rule. The pilot week (PRD section 10) is meant to catch these.

## 4. Connection key

Used to group bills that belong to the same customer visit.

Priority order: **VIN, then normalised vehicle number, then job card / invoice reference** (if one is present on the bill). The chosen key is stored with the bill. Dashboard groups bills that share a key. Normalisation means uppercase and with spaces, dashes and dots removed.

## 5. Data model (Supabase Postgres)

### `profiles`
| Column | Meaning |
|---|---|
| id | Same as the Supabase Auth user id |
| full_name | Display name |
| role | `service_advisor` or `cashier` |

### `uploads`
One row per uploaded PDF file.
| Column | Meaning |
|---|---|
| id | Unique id |
| uploaded_by | The advisor (profile id) |
| storage_path | Where the PDF is stored |
| original_filename | For display |
| file_hash | Detects duplicate uploads |
| page_count | Pages in the PDF |
| created_at | Upload time |

### `bills`
One row per bill. A PDF can produce several.
| Column | Meaning |
|---|---|
| id | Unique id |
| upload_id | Which PDF it came from |
| page_from, page_to | Page range inside that PDF |
| connection_key | Grouping key (section 4) |
| vin | As read, uppercase |
| vehicle_no_display | As printed |
| vehicle_no_norm | Uppercase, no spaces or dashes (used for search) |
| customer_name | As read |
| status | `needs_review`, `ready`, `paid` |
| uploaded_by | The advisor |
| paid_at | When the cashier marked it paid |
| paid_by | Cashier |
| delete_after | `paid_at` + 24 hours; empty until paid |
| created_at | Row creation time |

### Search indexes
- Trigram index on `customer_name` (partial and slightly misspelt names)
- Plain index on `vehicle_no_norm`
- Index on `vin`, plus an index on the last 6 characters of the VIN (computed column)
- Index on `connection_key`
- Index on `(status, delete_after)` for the purge job

### Search behaviour (one box, auto-detected)
| What the cashier types | How it is treated |
|---|---|
| 17 characters, VIN-shaped | Exact VIN match |
| 6 to 8 letters/digits ending in digits | Last-6 VIN match and vehicle number partial match |
| Looks like a registration number (after removing spaces) | Vehicle number match on `vehicle_no_norm` |
| Anything else | Name search using trigram similarity |

Results are merged and sorted by best match, then newest.

## 6. Storage

- One **private** Supabase Storage bucket for PDFs. Nothing is publicly readable.
- Path pattern: `bills/<upload id>.pdf`
- The app gives the browser a **short-lived signed link** to view or print a PDF.
- For printing a single bill out of a multi-bill PDF, the server uses **pdf-lib** to make a temporary copy with only that bill's pages. It is not stored.

## 7. Security and access (Row Level Security)

Supabase Row Level Security rules enforce roles in the database, not just in the screens.

| Table | Service advisor | Cashier |
|---|---|---|
| uploads | Create; read own | Read all |
| bills | Create; read and edit own bills that are not paid | Read all; update status (paid, undo) |
| profiles | Read own | Read own |
| Storage bucket | Upload; read own files | Read all files |

Other points:
- No public sign-up; the team creates accounts.
- The role is read from `profiles`, never taken from the browser.
- The Supabase service key lives only on the server and in the purge job, never in the browser.
- All traffic is HTTPS.

## 8. Real-time updates

The cashier dashboard subscribes to **Supabase Realtime** on the `bills` table. When an advisor confirms an upload, the new bill appears on the cashier's list without a refresh. Status changes (paid, undo) update the list the same way.

## 9. Automatic deletion (one-day buffer)

```
Cashier taps "Mark as Paid"
        |
        v
bills.status = paid, paid_at = now, delete_after = now + 24h
        |
        v
(Every hour) pg_cron triggers the purge Edge Function
        |
        v
Edge Function: find bills where delete_after has passed
        |
        +--> remove the PDF file through the Storage API
        |    (only when no other bill in that upload is still unpaid)
        +--> delete the bill rows (and the upload row once empty)
```

Important details:
- Files must be removed through the **Storage API**, not by deleting rows directly in SQL; direct row deletion can leave the actual file behind.
- A PDF holding several bills is deleted only after **all** of its bills are past their delete time.
- **Undo** simply clears `paid_at` and `delete_after` and sets status back to `ready`, so it works any time before the purge.
- The purge writes a short log (count deleted, any errors) so failures are visible.
- Unpaid bills are never touched by the purge.

## 10. Request flows

### Upload
1. Advisor selects PDFs. The server authorises the upload and the browser sends each file directly to private Supabase Storage, avoiding the hosting function's request-size limit.
2. The processing route reads the private stored file, extracts text, finds bills and fields, computes the connection key and file hash.
3. Server returns the extraction preview.
4. Advisor corrects anything flagged and confirms.
5. Server writes `uploads` and `bills` rows. Realtime notifies the cashier.

### Find and settle
1. Cashier types in search. The app queries Supabase (RLS applied).
2. Cashier opens a result. App requests a signed link and shows the preview.
3. Cashier prints. The server builds a pages-only copy with pdf-lib and the browser print dialog opens.
4. Cashier taps Mark as Paid. Row updates; purge timing starts.

## 12. Build order (suggested milestones)

1. Supabase project: tables, roles, Row Level Security, private bucket
2. Login and role-based landing pages
3. Upload page and PDF reading on 5 to 10 real sample bills (this is the riskiest part, so do it early)
4. Manual-entry fallback and review screen
5. Cashier dashboard with search
6. Bill preview, print-only-this-bill, Mark as Paid, Undo
7. Realtime updates
8. Purge job and its log
9. Pilot with 2 advisors and the cashier, then adjust reading rules
